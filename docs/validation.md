## 模拟器实测

2026 年 11 月 26 日，在同一台 GKD Pixel 2 上使用 v0.3.2 双驱动镜像测试。系统的 2 GiB TF 交换区已开启，zRAM 和 TF 卡的实际优先级均为 100。[模拟器推荐设置](components.md#模拟器推荐设置)

### PPSSPP 1.20.4 · 《空之轨迹 FC》

使用官方 PPSSPP，游戏编号为 `ULJM05170`。两轮从同一即时存档进入开场室内卡西乌斯的对话，均使用 OpenGL、1 倍 PSP 分辨率，关闭跳帧和自动跳帧。下表取自 PPSSPP 的屏幕计数器，游戏目标为 30 FPS，100% 表示按原速运行。

| 场景（每种驱动的采样数） | Mesa 24.3.4 / Panfrost 帧率 | Mesa 模拟速度中位数 | Arm Mali-G31 帧率 | Mali 模拟速度中位数 |
| --- | ---: | ---: | ---: | ---: |
| 停在同一句对话（4 次） | 20 FPS | 65.7% | 30–31 FPS | 100.2% |
| 用手柄确认键推进（5 次） | 17–20 FPS | 59.6% | 28–31 FPS | 98.9% |

两轮都推进到卡西乌斯告诉艾丝蒂尔带回礼物，期间均未退出。本次覆盖开场室内剧情，战斗场景尚待验证。

### 吉里吉里 1.4.4 · 《千恋＊万花》

使用官方 ARMv7 版，游戏内存设置为 `memusage=low`。OpenGL 使用 `ogl_compress_tex=half` 和 `ogl_max_texsize=1792`，软件渲染使用 `software_compress_tex=lz4`。

| 系统驱动 | 游戏渲染方式 | 测试起点与结果 |
| --- | --- | --- |
| Mesa / Panfrost | OpenGL | 从标题点「新的游戏」后输入超时，Android 将退出原因记为应用无响应（ANR）。 |
| Arm Mali | OpenGL | 从「新的游戏」进入第一章，芦花的立绘和近景均可显示。后续对话中系统因内存压力终止进程（`LOW_MEMORY`）。 |
| Mesa / Panfrost | 软件 | 从「新的游戏」推进，越过芦花出场，到「真是好久没见了呢」时仍能继续操作。 |
| Arm Mali | 软件 | 从已有芦花存档继续，推进到她询问二人分别了几年之后，游戏仍在前台响应。 |

Mali OpenGL 退出时，系统的低内存日志记录该进程约有 497 MiB 驻留在物理内存，另有 191 MiB 已换出，并报告持续回收内存和页面频繁换入换出。退出前最后一次采样中，整机的 2 GiB TF 交换区用了约 217 MiB。Mali 软件渲染续玩时，一次进程采样确认游戏自身约有 310 MiB 换到了 TF 卡。

本次安装的吉里吉里 UID 为 `10108`。早期参考安装的 Mesa 兼容组件要求 UID 为 `10117`，两次安装的条件不同。[参考安装的兼容条件](components.md#官方吉里吉里-opengl-兼容修复)

## 存储卡交换区优先级

独立版的原有策略是 zRAM 优先级 100、TF 卡优先级 10。本版新增相同优先级选项，两处都设为 100，沿用原有 2 GiB 交换文件。升级后原有虚拟内存开关会保留，优先级初始采用原策略。操作和复核命令见[虚拟内存设置](build.md#配置-2-gib-存储卡交换区)。

在一台使用开源图形驱动和 75% zRAM 的 GKD Pixel 2 上，用官方版吉里吉里 1.4.4 的 OpenGL 模式载入《千恋＊万花》。两轮都从空的 TF 交换区开始。约 88 秒时，TF 默认优先级 10 的占用峰值为 0 MiB，同优先级 100 的峰值为 86.3 MiB。同期整张卡的累计写入分别为 4.7 MiB 和 159.5 MiB。相同优先级的首次载入在 225 秒内未验证到标题画面，因此单列为载入测试。

另一次在默认档进入第一章，验证章节标志后将 TF 优先级临时调为 100。160 次输入后，同一游戏进程仍可响应。又送入 28 次输入，观察到街景切换为人物出场，整段 TF 交换区占用峰值为 70.4 MiB。延长段最后两次采样的画面相同。此轮未记录到游戏进程因低内存退出或无响应；两档测试期间均观察到系统界面进程反复重启，长时间游玩和其他存储卡的表现仍待验证。

与该掌机系统匹配的镜像在独立虚拟卡上验证了四次启动。TF 交换区依次为关闭、优先级 10、优先级 100、优先级 100。设置在重启后生效，zRAM 全程保持优先级 100，四次关机均正常卸载数据卷。

## v0.3.2 驱动槽和 Mali 冷启动

在 119 GiB 实机卡上，旧版第一次进入 Mesa 后，Android 把第 10 分区当作便携存储挂载并创建了 12 个媒体目录。驱动所需的 11 个文件全部正确，但 128 MiB 分区中有 23 个 4 KiB 块被改动。将这一分区标为系统保留并恢复其完整内容后，默认 Mesa 正常启动，存储管理器不再列出该分区。试用前后的完整驱动分区 SHA-256 均为 `ed51573d66661ca97d139ef17ceeaf986d7b2c953abf354cec035b1bf64e55c0`。

同一台实机从 Mesa 热重启试用时出现过黑屏。引导程序读入了内核、设备树和启动文件，三项 CRC 都正确。保留相同文件，从完全关机状态启动后，Android 报告 `ro.boot.pixel2gpu=trial`、`sys.boot_completed=1`。AT4K 位于前台，SurfaceFlinger 报告 **ARM, Mali-G31, OpenGL ES 3.2**，`/vendor` 的实际设备为只读的 `179:10`。同一张卡跑 Mesa 时，SurfaceFlinger 报告 **Mesa, Mali-G31 (Panfrost), OpenGL ES 3.1 Mesa 24.3.4**，使用只读的逻辑 vendor 分区。热启动时具体是哪一项硬件状态导致停住，尚未确定。

Windows 安装助手和独立组装流程生成的 v0.3.2 双驱动整卡均为 7 GiB，SHA-256 为 `2327fb2dc0d487ce13ec46e91f5b17f1e4ad7c531d27f2444ce157b700265bf3`。在 ARM 虚拟卡上依次验证默认 Mesa、一次性试用 Mali、未确认后回退 Mesa、再次试用、保留 Mali 并再次启动，以及从保留状态返回 Mesa。这六次检查覆盖切换逻辑。实际图形渲染器由掌机上的 SurfaceFlinger 核对。

用 Windows 助手生成的最终镜像全新刷写了一张 119 GiB TF 卡。从读卡器重新打开设备，读回全部 7,516,192,768 字节，SHA-256 与上面的整卡一致，两份分区表也通过校验。该次全新安装的掌机验收结果见[版本发布说明](https://github.com/JackyChenXY/gkd-pixel2-gammaos/releases/tag/v0.3.2)。

这张全新刷写的卡首次使用 Mesa。正式版引导的两次 Mali 冷启动试用中，第一次持续黑屏，随后实测回到 Mesa。两次之间临时加入引导日志，成功进入 Mali，并确认内核、设备树和启动包的长度及 CRC 均与发布镜像相符。恢复原版引导并核对 SHA-256 后，第二次正式版试用进入 AT4K。调试接口报告启动完成、屏幕开启、只读的 `/vendor` 设备号为 `179:10`，实际渲染器为 **ARM, Mali-G31, OpenGL ES 3.2**。首次冷启动黑屏的原因仍未确定。

开启 USB 调试后可在电脑运行 `python3 port/gpu-selector/tests/check-device-slot.py --expect trial`，同时核对启动模式、只读挂载、便携存储列表和实际渲染器。验证默认 Mesa 时改用 `--expect mesa`。

## v0.3.1 AT4K 双驱动镜像

最初的候选版在 119 GiB 卡上启动后同时列出了 AT4K 和 Trebuchet。实机读数显示手柄辅助服务尚未启用，导航栏处于显示状态。修正版在系统主屏角色与新用户初始设置中处理这两项缺省值。AT4K 保留原 APK 签名，系统壁纸与 H700 安装包中的原图逐字节相同。

在同一张卡上启用手柄服务后，用内置手柄转发设备送入间隔 50 毫秒的 R1 和功能键，实机显示返回、桌面和最近任务菜单。已确认方向键移动 AT4K 的应用焦点，A 打开文件管理器，B 返回桌面。在最近任务中，左、右键切换设置和时钟，X 移除选中的时钟任务，B 返回 AT4K。概览显示了可用物理内存、总量和 TF 交换状态。

Windows 助手与独立组装流程分别生成了相同的 7 GiB 整卡，SHA-256 均为 `0bd96facdf47b3670c5e362fe40456ba85976e72f8bc22ecbbd47355ecb05e17`。修正版通过了 ARM 虚拟卡的默认 Mesa、试用 Mali 和未确认后回退 Mesa 三轮启动检查。

同一张 119 GiB 卡全新刷入修正版，整段读回校验通过。实机首次解锁仍出现 AT4K 和 Trebuchet 的选择器。选 AT4K，再点「始终」即可保存。用户确认 H700 壁纸正确，右侧三键栏已隐藏，并且无需手动启用服务就能用 R1＋功能键打开菜单、进入最近任务。本轮面板与按键验收使用默认 Mesa。

解锁并启用 USB 调试后，下面的只读检查可以核对桌面、原图校验值和手柄服务。若还没选择默认桌面，检查会提示完成选择。选「始终」后，可加 `--expect-saved-home` 核对保存的主屏。

```sh
python3 port/desktop/at4k/check-device.py
```

## v0.3.0 整卡检查

Windows 安装助手已在 Windows x64 上生成 7 GiB 双驱动镜像。独立实现逐项验证了 11 个驱动文件、完整的 128 MiB 备用 vendor 和启动选择扇区。Windows 生成的镜像读回 SHA-256 与独立实现一致。公开基础镜像使用空槽和默认 Mesa，两个镜像的数据分区均为首次开机准备的空白状态。

同一张虚拟卡已通过六次启动检查，依次覆盖出厂预装、首次试用、未确认回退、确认保留、保留后再启动和手动返回 Mesa。Android 图形设置服务每次都返回了预期状态。真实面板显示、Mali 冷启动以及具体游戏性能仍需在 GKD Pixel 2 上复测。下文的实机体验来自这台掌机上此前测试的相应组件。

## 复核

设备启动完成、解锁并授权 USB 调试后，可从电脑检查：

```bash
adb shell getprop sys.boot_completed
adb shell getprop ro.lineage.version
adb shell getprop ro.gsid.image_running
adb shell getprop ro.crypto.metadata.enabled
adb shell cat /proc/swaps
adb shell cat /proc/meminfo
```

完成独立启动时，`sys.boot_completed` 应为 `1`，`ro.gsid.image_running` 应为 `0`。`MemTotal` 表示内核可用物理内存，`SwapTotal` 表示交换空间总量。两种交换设备可用 `/proc/swaps` 分辨。对离线的 `system.img` 可运行 `e2fsck -fn`，对打包后的 `super.raw.img` 可用 `lpdump --slot=0` 和 `lpdump --slot=1` 核对两个逻辑分区表。

## 已知限制

- 当前为 `userdebug/test-keys` 构建，Android 安全补丁日期为 `2023-11-05`。SELinux 使用 permissive，尚未建立完整的 AVB 强制验证链。USB 调试使用设备端授权。
- 交换文件位于启用元数据加密的 F2FS 数据卷中。开启后会占用 TF 卡空间。本次对照使用同一张卡，其他卡速及模拟器负载仍待验证。
- 实机验证基于一台 GKD Pixel 2。不同屏幕批次和存储卡的兼容性待验证。

## 开源驱动实机结果

- 116.5 GiB 测试卡已用 Mesa 24.3.4 冷启动到桌面，原版 glmark2 完成 33 个场景。系统使用 Panfrost，GLES 1、2、3 的像素读回和 ES 3.1 计算结果均已核对。[驱动、对照条件和测量值](../port/open-variant/vendor/pixel2-system-gpu/)
- Quickstep 最近任务已在实机显示物理内存可用量和 TF 卡交换用量，可用手柄切换和关闭所选任务。内存解析测试覆盖空表、关闭、低于 1 MiB 以及启用两种交换优先级的情况。[截图与操作说明](components.md)
- 已在参考安装验证官方吉里吉里 1.4.4 的图标启动和《千恋＊万花》自动剧情。驱动、APK 散列和参考安装 UID 是此次测试的版本条件。[兼容目录](../port/open-variant/krkr2/)

### 桌面和渲染组件的离线复核

两个 APK 都通过 Android 签名验证。Trebuchet 的四个补丁按顺序应用到原版源码，八项内存计数测试全部通过。下载包中的系统驱动组装器在匹配的 vendor 镜像上检查了 914 个条目、五个 ARM32 图形库、GLES 3.1 声明和 SELinux 标签。吉里吉里修复的 system 组装器检查了基线中 4,933 个条目，并验证 ext4、AVB 签名和纠错数据。两次组装均在电脑上操作普通镜像文件。

此前曾出现桌面系统设置图标名称错误。参考机上刷新 Android 为 Settings 保留的旧资源编号缓存并重启界面后，桌面恢复了正确名称。新安装或其他固件的缓存状态可能不同。
